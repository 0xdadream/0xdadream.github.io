2026 AI Coding CLI 完整指南：主流终端 Agent 安装、使用、选择与避坑

本文整理目前主流的 AI Coding CLI / Terminal Agent。这类工具与普通聊天机器人最大的区别是：它们不仅能回答问题，还可以读取项目、修改文件、运行终端命令、执行测试、操作 Git，并通过 MCP、Skills、Hooks、Subagents 等机制扩展能力。

本文主要面向 Windows 10/11 + PowerShell / WSL2，同时给出 Linux、macOS 用户可以复用的思路。命令和产品状态已复核到 2026-08-25；这类工具更新非常快，安装前仍建议打开对应官方文档确认最新要求。

本文把工具分成两层：Claude Code、Codex、Antigravity、Grok Build、Copilot CLI、Cursor CLI、OpenCode、Qwen Code、Cline、Kiro、Aider、Pi、Amp、goose 属于本文核心 Coding CLI；OpenClaw、Hermes 更接近常驻 Agent/Gateway 平台，放进来是为了补全终端 Agent 生态，而不是把它们和纯 Coding CLI 强行放在同一赛道比较。

重要：文中出现的 irm ... | iex、iwr ... | iex、curl ... | bash 都属于“下载远程脚本并立即执行”。只应使用产品官方域名；公司设备或高安全环境优先选择 WinGet、官方安装包、Release 二进制，或先把脚本下载到本地审阅后再执行。

这里的“无官方 npm 入口”指官方没有把 npm 全局安装作为面向最终用户的安装路径，不代表项目源码内部完全不使用 Node/npm。Hermes 就是典型例子：安装器会准备 Node 依赖，但这不等于存在 npm install -g hermes-agent 这种官方安装方式。

先看结论：按需求选，不要按数量装

你的需求 优先看 原因
想要厂商官方、开箱即用 Claude Code / Codex / Antigravity / Grok Build 模型、认证、Agent Harness 一体化
GitHub 工作很多 Copilot CLI GitHub 身份、仓库、PR/Issue 工作流衔接自然
已经在用 Cursor Cursor CLI 与 Cursor 账号、规则和 Agent 工作流一致
想自由换模型/API OpenCode / Cline / Aider / Pi / goose Provider 选择多，适合 BYOK 和自建端点
国内模型/ModelStudio Qwen Code 国内访问、Qwen 与 ModelStudio 生态更友好
强调 Git 可追踪和可回退 Aider 工作方式天然围绕 Git diff/commit
喜欢自己搭 Agent Harness Pi 核心很小，扩展、Skills、模板自由度高
想做常驻个人 Agent/Gateway OpenClaw / Hermes 已经超出单纯 Coding CLI 范畴

如果只是第一次接触，先选 1 个官方 CLI + 1 个多 Provider CLI 就够了。例如 Codex + OpenCode、Claude Code + Qwen Code，比同时装十几个更容易维护。

二、Windows 使用 AI CLI 前先准备环境

建议至少安装 Git、PowerShell、Node.js 和 Python：

winget install Git.Git
winget install Microsoft.PowerShell
winget install OpenJS.NodeJS.LTS
winget install Python.Python.3.12

检查环境：

git --version
node --version
npm --version
python --version
pwsh --version

如果经常运行开源 Agent、Linux 工具链、Docker 或大型仓库，再安装 WSL2：

wsl --install

Windows 原生和 WSL 不要混着跑同一个仓库

同一个项目最好固定在一个主要执行环境里：Windows 原生 Agent 就操作 D:\Projects\xxx，WSL Agent 就操作 Linux 文件系统中的 ~/projects/xxx。不建议一会儿从 PowerShell 打开 E:\repo，一会儿又让 WSL 中的 Agent 通过 /mnt/e/repo 修改同一工作树。

混用容易碰到换行符、文件权限、大小写、软链接、文件监听、Git 可执行位和 Node/Python 环境差异。需要同时比较多个 Agent 时，更推荐 git worktree 为它们创建独立工作树，而不是让多个高权限 Agent 同时编辑同一目录。

不要重复安装同一个 CLI

很多“升级后版本没变化”的问题，本质上是系统里同时存在 npm 版、独立 exe 版、WinGet 版或旧 PATH。排查时先运行：

Get-Command codex -All
Get-Command claude -All
where.exe codex
where.exe claude

原则是：同一个 CLI 尽量只保留一种安装渠道。

三、Claude Code

Claude Code 是 Anthropic 官方终端 Coding Agent。Windows 目前可以直接使用官方安装脚本或 WinGet。

irm https://claude.ai/install.ps1 | iex
# 或
winget install Anthropic.ClaudeCode

验证与启动：

claude --version
cd D:\project
claude

适合先让它只读分析，再逐步授权修改：

先完整阅读项目结构，不修改任何文件。
告诉我核心入口、构建方式、测试方式和风险点。

长期项目可以在仓库中维护 CLAUDE.md，记录项目规则、测试命令、禁止修改区域和代码风格。

注意：不要把 --dangerously-skip-permissions 之类的跳过授权模式作为日常默认。陌生仓库尤其应该保持人工确认。

官方文档：Claude Code

四、OpenAI Codex CLI

Codex CLI 是 OpenAI 官方本地 Coding Agent。Windows 推荐官方 PowerShell 安装器：

powershell -ExecutionPolicy ByPass -c "irm https://chatgpt.com/codex/install.ps1 | iex"

也可以使用 npm：

npm install -g @openai/codex

启动：

codex --version
cd D:\project
codex

长期项目建议准备 AGENTS.md，把仓库约束、测试命令、目录边界和提交要求写进去。ChatGPT 订阅与 OpenAI API Key 计费是两条不同的认证/计费路径，使用 API Key 时应单独关注 API 消耗。

官方仓库：openai/codex

五、Google Antigravity CLI

Google 已经把个人终端 Agent 的主路线从 Gemini CLI 转向 Antigravity CLI。其启动命令是 agy。

Windows 安装：

irm https://antigravity.google/cli/install.ps1 | iex

验证并启动：

agy --help
cd D:\project
agy

默认会把程序安装到当前用户的本地目录，并通过 Google 登录或系统安全凭据完成认证。它支持项目会话、Agent、Skills、MCP、后台任务等能力。

一个非常重要的时间点是：从 2026-06-18 起，Gemini CLI 不再为 Google AI Free、Google AI Pro、Google AI Ultra 的个人账户提供原来的服务路径，这些个人层级被迁移到 Antigravity CLI；Gemini Code Assist 企业许可与 API Key 使用仍可继续使用 Gemini CLI。

从 Gemini CLI 迁移

第一次运行 agy 时会检测部分旧配置。如果以前装过 Gemini CLI，还可以显式导入扩展：

agy plugin import gemini

Antigravity 把 Gemini CLI 的 extensions 迁移为 plugins。项目级 Skills 目录也发生了变化：旧的 .gemini/skills/ 应迁到 .agents/skills/；自定义 MCP 配置则使用 .agents/mcp_config.json。迁移不是所有 UI/主题配置都能 1:1 对应，所以老用户最好迁移后再逐项检查 Skills、Hooks 和 MCP 是否真正生效。

使用 Gemini API Key 的一个易踩坑点

如果不走 Google 账号登录，而是希望 Antigravity 直接使用 Gemini API Key，只设置 GEMINI_API_KEY 并不会自动切换到 API Key 模式。还要在 ~/.gemini/antigravity-cli/settings.json 中显式指定 Provider：

{
  "modelProvider": "gemini"
}

然后在当前 PowerShell 会话中设置：

$env:GEMINI_API_KEY = "YOUR_API_KEY"
agy

如果 modelProvider 仍是 gemini，但环境变量里已经没有 GEMINI_API_KEY，CLI 会在启动阶段报错。需要恢复账号登录时，应删除这个 modelProvider 配置并重新启动。API Key 不要直接写进仓库、.env 示例或公开截图。

官方文档：Antigravity CLI Getting Started · Installation & Auth · Gemini CLI Migration

六、Gemini CLI

Gemini CLI 仍然存在，尤其对企业用户、Gemini Code Assist 以及 API Key 用户仍有价值。

npm 安装：

npm install -g @google/gemini-cli

启动：

gemini --version
gemini

如果是个人 Google AI Free / Pro / Ultra 用户，现在应该优先使用 agy；如果是企业环境、Google Cloud 或 API Key 工作流，再继续保留 gemini 更合理。

迁移公告：Transitioning Gemini CLI to Antigravity CLI

七、Grok Build

Grok Build 是 xAI 官方 Coding Agent，启动命令是 grok。Windows 官方提供原生 PowerShell 安装器：

irm https://x.ai/cli/install.ps1 | iex

验证与启动：

grok --version
cd D:\project
grok

常用命令：

grok login
grok logout
grok inspect
grok models
grok update

单次非交互任务：

grok -p "Explain this codebase"

grok inspect 很适合排查当前项目到底加载了哪些 Rules、Skills、Plugins、Hooks 和 MCP。Grok 也支持在配置中定义自定义模型或兼容端点。

官方文档：Grok Build

八、GitHub Copilot CLI

GitHub Copilot CLI 已经是完整的终端 Agent，而不是早期只帮助生成 shell 命令的辅助工具。

Windows 推荐：

winget install GitHub.Copilot

或者使用 npm（要求较新的 Node.js）：

npm install -g @github/copilot

启动与登录：

copilot

进入 CLI 后执行：

/login

它适合 GitHub 仓库、Issue、PR、Actions 等工作流，并支持项目指令、Skills、Custom Agents、Hooks 与 MCP。需要脚本化时可以直接执行：

copilot -p "review the current git diff and list possible regressions"
copilot -sp "explain this repository in five bullet points"

其中 -p 是非交互执行后退出，-s 适合脚本管道，只输出 Agent 响应。Copilot CLI 还区分工具、文件路径和 URL 权限；首次进入目录时的 Trust 提示不要无脑确认，陌生仓库要先检查内容。

尤其不要把下面的模式做成默认别名：

copilot --allow-all
copilot --yolo

它们会同时放开工具、路径和 URL 审批。确实需要高自主执行时，更合理的是在隔离环境里使用。

Copilot CLI 还提供本地 Sandbox，把 Agent 代你运行的命令和工具放进操作系统级沙箱。当前这是 Public Preview / Experimental 功能，需要先用 --experimental 启动，或在会话里执行 /experimental on，然后再：

/sandbox enable
/sandbox policy

这里有一个 Windows 重要限制：当前本地 Sandbox 在 Windows 上要求 Windows Insider build。普通稳定版 Windows 11 如果无法开启，不要误以为 Copilot CLI 安装坏了；这时仍应通过普通用户权限、独立工作目录、Git Worktree、WSL/容器等方式隔离高风险任务。

官方文档：GitHub Copilot CLI · Local Sandboxing

九、Cursor CLI

Cursor CLI 可以在终端里直接调用 Cursor Agent，支持交互式开发以及脚本/CI 场景。当前官方主命令已经是 agent；网上旧教程里常见的 cursor-agent 属于旧命令或旧版本资料，排错时要先确认自己安装的是哪一代 CLI。

Windows 现在已经有原生 PowerShell 安装方式：

irm 'https://cursor.com/install?win32=true' | iex

macOS、Linux 与 Windows WSL 使用：

curl https://cursor.com/install -fsS | bash

验证、启动和手动升级：

agent --version
cd D:\project
agent
agent update

也可以直接带初始任务启动：

agent "review the authentication module and list security risks"

Cursor CLI 默认会自动尝试更新；如果环境检测器一直显示旧版本，再用 Get-Command agent -All / where.exe agent 检查 PATH 中是否存在多份程序。CLI 具有修改文件和执行命令的能力，因此 CI、陌生仓库和带生产凭据的目录仍应遵循最小权限原则。

官方文档：Cursor CLI Overview · Installation

十、OpenCode

OpenCode 是目前非常活跃的开源多 Provider Coding Agent。Windows 原生可以通过 npm、Scoop、Chocolatey 等方式安装，但官方仍建议 Windows 用户优先使用 WSL 获得完整兼容性。

npm install -g opencode-ai

启动：

opencode

进入 TUI 后使用：

/connect

连接需要的模型 Provider。它适合同时使用 OpenAI、Anthropic、OpenRouter、本地模型或其他兼容 Provider 的用户。

截至本文更新时间，OpenCode 2 仍属于 Beta，使用独立的 opencode2 命令，不会覆盖稳定版 opencode。普通日常环境建议优先稳定版。

官方文档：OpenCode

十一、Qwen Code

Qwen Code 是 Qwen 官方 Agentic Coding CLI，Windows 可以直接使用独立安装脚本，也可以使用 npm。

推荐的 Windows PowerShell 安装：

irm https://qwen-code-assets.oss-cn-hangzhou.aliyuncs.com/installation/install-qwen-standalone.ps1 | iex

npm 安装要求 Node.js 22+：

npm install -g @qwen-code/qwen-code@latest

验证与启动：

qwen --version
cd D:\project
qwen

首次启动会引导配置 ModelStudio 等认证方式。对于希望使用国内模型生态、阿里云 ModelStudio 或兼容 API 的用户，Qwen Code 很值得保留。

官方文档：Qwen Code Quickstart

十二、Cline CLI

Cline 除了 IDE 插件，现在也有正式 CLI，可交互运行，也可以用于脚本和 CI/CD。

安装：

npm install -g cline

认证与启动：

cline auth
cline

单次任务：

cline "Audit this package and propose fixes"

Cline 支持 Cline、OpenAI、Anthropic、Gemini、OpenRouter、Bedrock、Vertex 和 OpenAI-compatible 等 Provider。它的优势是 Provider 选择灵活，同时保留 Plan/Act、Rules、MCP、Checkpoints 等 Agent 工作流。

当前 npm 包本身主要负责选择与你平台匹配的已编译二进制，Windows x64/ARM64、Linux 和 macOS 都有对应包。普通用户安装 Cline CLI 不需要另外安装 Bun 或 Zig；这些更多是从源码开发/构建 CLI 时才需要的工具。如果安装后提示找不到平台二进制，优先检查 npm 的 optional dependencies 是否被禁用或安装是否完整，而不是盲目补开发工具链。

官方仓库：Cline CLI

十三、Kiro CLI

十七、goose

goose 是 Agentic AI Foundation / Linux Foundation 体系中的开源通用 Agent。它不只面向写代码，也适合研究、自动化、数据处理和 MCP 工作流。

官方 CLI 当前使用 AAIF 仓库的稳定版安装脚本。Windows 可以在 Git Bash、MSYS2，或具备 Bash 环境的 PowerShell 中执行：

curl -fsSL https://github.com/aaif-goose/goose/releases/download/stable/download_cli.sh | bash

这里有一个 Windows 小坑：命令最后仍然调用 bash。如果 PowerShell 提示“找不到 bash”，不是 goose 本身坏了，而是当前 PATH 里没有 Bash；改到 Git Bash / MSYS2 执行，或先准备可用的 Bash 环境。

goose configure

启动会话：

goose session

查看环境信息：

goose info

它支持 Anthropic、OpenAI、Google、OpenRouter、本地模型以及大量 MCP 扩展。如果希望一个 Agent 同时覆盖代码、自动化和通用任务，goose 很有价值。

官方资料：goose / aaif-goose

十八、OpenClaw

OpenClaw 与普通 Coding CLI 不完全是同一类产品，它更像 本地 AI Gateway + Agent 平台，可以长期运行 Gateway、接入多个聊天渠道、路由多个 Agent，并连接 Provider、Skills 和 MCP。

Windows 推荐安装：

iwr -useb https://openclaw.ai/install.ps1 | iex

安装后可以运行：

openclaw --version
openclaw doctor
openclaw onboard --install-daemon
openclaw gateway status

如果已经自行管理 Node，也可以直接使用 npm。当前官方要求 Node 22.22.3+、24.15+ 或 25.9+，并推荐 Node 26。npm 12 或 npm 11.16+ 可使用：

npm install -g openclaw@latest --allow-scripts=openclaw
openclaw onboard --install-daemon

旧版 npm 11.15 及更早版本没有 --allow-scripts 参数，应去掉该参数。这里不是普通的“随便 npm -g 一下”场景：OpenClaw 有 lifecycle scripts，npm 版本与脚本许可策略不匹配时会出现安装完成但关键步骤被阻止的问题。普通用户仍优先官方 installer 更省事。

因为它可能长期运行 Gateway，所以必须额外注意监听地址、Token、聊天平台权限、API Key、远程访问和 MCP 权限。不要把无认证 Gateway 直接暴露到公网。

官方文档：OpenClaw Install

十九、Hermes Agent

Hermes Agent 是 Nous Research 的通用 Agent，覆盖 Coding、终端工具、长期记忆、Skills、Gateway、定时任务与多 Provider。它和 OpenClaw 一样，不应只当成一个“写代码命令行”。

安装方式：官方目前不提供面向最终用户的 npm 全局安装

macOS / Windows 如果同时想要 Desktop 和 CLI，官方当前首先推荐 Hermes Desktop 安装器；只想安装 CLI 时再使用下面的脚本。CLI-only 安装完成后，也可以随时运行 hermes desktop 安装并启动 Desktop。

Windows 原生 PowerShell 安装：

iex (irm https://hermes-agent.nousresearch.com/install.ps1)

Linux、macOS、WSL2 使用官方安装器：

curl -fsSL https://hermes-agent.nousresearch.com/install.sh | bash

截至 2026-08-25，Nous Research 官方 Hermes Agent 没有类似 npm install -g hermes-agent 的正式分发方式。官方仓库虽然存在 package.json，但根包标记为 private: true，它是项目内部的 Node workspace，用来管理 Desktop/TUI/Web 等依赖，不是给用户全局安装 CLI 的 npm 包。

需要注意一个容易误解的地方：Hermes 官方安装器内部确实会安装 Node.js 并运行 npm 来准备部分依赖，所以日志里看到 npm install 很正常；这只是安装器实现细节，不代表官方支持用户自己执行 npm install -g hermes-agent。同理，官方 Quickstart 也明确不建议把 Hermes 当普通 PyPI 包直接 pip install hermes-agent。

因此需要特别注意：不要因为 npm/PyPI 搜索结果里出现 hermes、hermes-cli、hermes-agent 等相似名字，就直接把它当成 Nous Research 官方包。安装前必须核对官方文档、发布者和仓库地址，否则很容易装到同名但完全无关的项目，甚至让别的包抢占系统里的 hermes 命令。官方当前推荐 Desktop 安装器或上述 install.ps1 / install.sh。

首次配置与基础命令

hermes --version
hermes setup
hermes setup --portal
hermes model
hermes tools
hermes doctor
hermes desktop
hermes

hermes setup --portal 是官方给出的最快入门路径，会完成 Nous Portal 登录并配置基础 Provider；hermes model 用来新增或切换 Provider、完成 OAuth、配置 API Key 和自托管 endpoint；hermes tools 管理启用的工具；hermes doctor 用于诊断安装、配置和运行环境。

单次非交互调用：

hermes chat -q "分析当前项目"
hermes -z "只输出最终结果，适合脚本/CI"
hermes chat --model "anthropic/claude-sonnet-4" -q "检查这个仓库"
hermes chat --provider openrouter -q "总结当前代码"

hermes -z <prompt> 是更纯粹的脚本化 one-shot 入口：单个 Prompt 输入、最终文本输出，适合 shell、CI、cron 和父进程调用。需要排查“到底是 Hermes 本身还是个人配置导致的问题”时，还可以使用：

hermes chat --safe-mode -q "复现这个问题"
hermes chat --ignore-user-config --ignore-rules -q "在隔离配置下测试"
hermes chat --checkpoints -q "修改前创建文件系统检查点"

会话与工作流常用参数：

hermes --continue
hermes --resume <SESSION_ID>
hermes --worktree
hermes --profile <NAME>
hermes -s <SKILL_NAME>
hermes --tui

Gateway 与配置：

hermes gateway setup
hermes config get <KEY>
hermes config set <KEY> <VALUE>

进入交互会话后，/model 只能在已经配置好的 Provider/模型之间切换；如果要新增 Provider、执行 OAuth 或录入 API Key，应退出会话后运行 hermes model。

Hermes 会维护自己的配置、凭据、Memory、Skills、Sessions 和 Logs。长期 Agent 状态越多，越要重视本地隐私、凭据目录和 Gateway 暴露范围；--yolo 等跳过危险命令审批的模式不要作为默认配置。

官方文档：Hermes Agent Installation · CLI Commands Reference

openclaw channels status --probe
openclaw dashboard             # 打开 Dashboard
openclaw update                # 更新
openclaw --version

OpenClaw 是常驻 Gateway 平台，最有价值的不是记住所有子命令，而是记住故障排查顺序：status → gateway status → logs --follow → doctor → models status。如果 Gateway 对外监听，必须再检查认证、绑定地址和远程访问边界。

Hermes Agent 常用命令

hermes                         # 交互模式
hermes --tui                   # 新 TUI
hermes chat -q "分析当前项目"  # 单次非交互调用
hermes setup                   # 完整配置向导
hermes setup --portal          # Nous Portal 快速配置
hermes model                   # Provider/模型/OAuth/API Key
hermes tools                   # 工具配置
hermes doctor                  # 诊断
hermes --continue              # 继续最近会话
hermes --resume <SESSION>      # 恢复指定会话
hermes --worktree              # 独立 Git Worktree 模式
hermes gateway setup           # Gateway 配置
hermes config get <KEY>        # 读取配置
hermes config set <KEY> <VALUE># 修改配置
hermes --version

再次强调：官方 Hermes Agent 当前没有正式的 npm 全局安装命令。npm 上名字带 hermes 的包不能凭名字认定为 Nous Research 官方 CLI；安装前必须核对发布者与官方文档。

二十、到底应该安装哪些？

完全没有必要把所有 CLI 都作为日常工具。更合理的方式是覆盖不同生态：

需求 推荐
OpenAI 官方体验 Codex
Claude 官方体验 Claude Code
Google 官方个人终端路线 Antigravity CLI
Grok Grok Build
GitHub 深度工作流 Copilot CLI
多 Provider OpenCode / Cline
国内模型与 ModelStudio Qwen Code
Git 强控制 Aider
极简可扩展 Harness Pi
通用本地 Agent goose
长期 Gateway/个人 Agent OpenClaw / Hermes

如果只装 5 个，比较均衡的组合是：Claude Code + Codex + Antigravity + OpenCode + Qwen Code。如果 GitHub 工作流很多，再加 Copilot CLI；如果喜欢研究 Agent Harness，再看 Pi、goose、OpenClaw 和 Hermes。

安装免费不等于模型调用免费

这里还要区分三个概念：CLI 软件本身、账号订阅权益、API/BYOK 调用费用。OpenCode、Aider、Pi、goose 这类客户端即使本身开源免费，连接商业模型时仍可能产生 Provider API 费用；而 Claude Code、Codex、Copilot、Cursor、Antigravity、Kiro 等产品可能提供账号登录或订阅内权益，但具体额度和可用模型会随套餐变化。

因此不要根据“CLI 能免费下载”推断“AI 使用永久免费”。部署到 CI/CD 前尤其要确认它到底在消耗订阅额度、AI Credits，还是单独的 API 账单，并给自动化任务设置预算、超时和最大迭代次数。

二十一、推荐的标准 Agent 工作流

不要直接对一个重要项目说“把整个项目优化到最好”并授予全部权限。更可靠的顺序是：

1. 保证 Git 工作区干净
2. 建立新 Branch 或 Worktree
3. 先只读分析
4. 让 Agent 给出修改计划
5. 人工检查计划
6. 再允许修改
7. 运行测试、Lint、构建
8. 查看 git diff
9. 必要时让另一个 Agent 做 Code Review
10. 人工确认后 Commit

例如：

git status
git switch -c ai/refactor-auth

第一轮提示词：

第一阶段只允许分析，不修改代码。
请阅读认证相关代码，列出问题、涉及文件、修改方案和验证方法，然后等待我确认。

确认后再继续：

按照刚才方案实施，禁止修改方案之外的文件。
完成后运行已有测试，并给出 git diff 摘要。

这个方法对 Claude Code、Codex、Antigravity、Grok、Copilot、OpenCode、Qwen Code、Cline 等都适用。

一套可以跨 CLI 复用的四阶段提示词

阶段 1：只读摸底

先不要修改任何文件。阅读项目目录、README、依赖配置、入口文件和测试配置。
输出：项目架构、启动/构建/测试命令、关键模块、当前风险和你还不确定的地方。

阶段 2：形成可验证计划

针对目标问题给出修改计划。逐项列出：要改的文件、为什么要改、可能影响什么、如何验证。
不要实施，等我确认。

阶段 3：实施并自证

按确认后的计划实施，不扩展任务范围。修改后运行与本次改动直接相关的测试、Lint 和构建。
如果验证失败，先解释原因再继续修复，不要为了让测试通过而删除测试或降低检查标准。

阶段 4：交付审查结果

停止继续修改。审查 git diff，列出实际修改、验证结果、仍存在的风险、未完成事项，以及是否出现计划外文件改动。

这种提示方式的重点不是“限制 AI 发挥”，而是让分析、实施、验证和审查之间形成清晰边界，出问题时更容易定位和回退。

二十二、所有 AI CLI 都应该遵守的安全规则

AI Coding Agent 可能拥有读文件、写文件、删除文件、PowerShell/Bash、Git、网络、MCP、浏览器甚至云资源权限，因此应把它当成“能够操作电脑的自动化程序”，而不是普通聊天框。

1. 不要从用户主目录直接启动

不推荐：

cd C:\Users\YourName
claude

更合理：

cd D:\Projects\MyProject
claude

2. 不要把 API Key 提交到 Git

至少把常见环境变量文件加入 .gitignore：

.env
.env.*

生产密钥、SSH 私钥、浏览器 Profile、钱包私钥、密码库等不要放在 Agent 默认工作目录。

3. MCP 是新的权限边界

一个 MCP Server 可能拥有 GitHub、数据库、Cloudflare、浏览器、文件系统、SSH、Slack 或云资源权限。接入越多并不等于越强，通常也意味着更大的攻击面与 Prompt Injection 风险。

只开启当前任务真正需要的 MCP。

4. 谨慎使用 Auto Approve / YOLO

不同产品可能叫：dangerously-skip-permissions、always approve、trust all tools、force、YOLO 等。本质都是减少人工审批。陌生仓库、外部网页、第三方 MCP 或带生产凭据的环境不要默认启用。

5. 陌生代码最好隔离运行

优先考虑 WSL2、Docker、Dev Container、虚拟机、Sandbox 或临时 Worktree，尤其是安全研究样本、来路不明 GitHub 仓库和自动执行脚本。

二十三、升级后为什么还是旧版本？

Windows 最常见的原因是 PATH 中存在多份同名程序。比如管理器显示 Codex 已升级，但命令行仍是旧版，先检查：

codex --version
Get-Command codex -All
where.exe codex

如果输出类似：

C:\Users\xxx\AppData\Roaming\npm\codex.cmd
C:\Users\xxx\.local\bin\codex.exe

说明存在重复安装。再看 npm：

npm list -g --depth=0
npm root -g
npm config get prefix

正确处理思路是确认当前真正执行的路径，保留一种安装渠道，卸载其余重复版本，然后重新打开终端再检查。

二十四、一次检查所有常用 CLI

下面的 PowerShell 可以快速检查命令是否可执行，以及当前命令实际来自哪里：

$commands = @(
    "claude", "codex", "agy", "gemini", "grok",
    "copilot", "agent", "opencode", "qwen", "cline",
    "kiro-cli", "aider", "pi", "amp", "goose",
    "openclaw", "hermes"
)

foreach ($cmd in $commands) {
    $result = Get-Command $cmd -ErrorAction SilentlyContinue
    if ($result) {
        Write-Host "[OK] $cmd -> $($result.Source)"
    } else {
        Write-Host "[--] $cmd -> Not Installed"
    }
}

如果还要做“本地环境检查器”，建议不要只看 npm 包是否安装，而应优先使用 Get-Command / where.exe 判断当前 Shell 能否真正执行，再分别调用各 CLI 的 --version 获取版本。

二十五、2026 年几个必须知道的变化

Gemini CLI → Antigravity CLI

个人 Google AI Free / Pro / Ultra 用户的官方终端路线已经迁移到 Antigravity CLI；Gemini CLI 主要继续服务企业许可和 API Key 场景。因此新的环境检测器应该同时检测 agy 与 gemini，但默认推荐个人用户优先 agy。

Windows 原生支持明显增强

Claude Code、Codex、Antigravity、Grok Build、Copilot CLI、Cursor CLI、Qwen Code、Cline、Kiro、OpenClaw、Hermes 等都已经提供 Windows 原生安装路径。OpenCode 也能原生安装，但官方仍建议 Windows 用户优先考虑 WSL 以获得更完整的兼容性。

Agent 的“权限模型”比单纯模型能力更重要

选 CLI 时不要只看“哪个模型最聪明”，还要看 Sandbox、Permission、MCP、Hooks、Skills、Memory、Worktree、Git、Headless、CI/CD、Provider 和 Context 管理。

安装脚本比 npm 越来越常见

不少厂商开始优先提供独立二进制和官方安装脚本。原因包括启动更快、降低 Node 依赖、减少包管理冲突和方便自动升级。旧教程里“所有 CLI 都 npm -g”已经不再适用。

如果把当前 AI CLI 生态简单归纳：Claude Code、Codex、Antigravity 和 Grok Build 是主要厂商的官方旗舰；Copilot CLI 与 GitHub 工作流结合最紧密；OpenCode、Cline、Aider、Pi、goose 更适合多 Provider 和自定义 Agent 工作流；Qwen Code 对国内模型生态更友好；OpenClaw 与 Hermes 则进一步走向常驻 Gateway 和个人 Agent 平台。
